# Служба уведомлений

Отдельный процесс рядом с Supabase. Каждые несколько секунд:

1. переводит задачи ТО из «Запланировано» в «Новая», когда наступил период (раз в 10 минут, повторный запуск безопасен);
2. регистрирует просроченные задачи (уведомление руководителям);
3. забирает события из очереди `integration_outbox`, раскладывает их по получателям (`load_email_event_plan`, `load_telegram_event_plan`) и отправляет письма и сообщения Telegram. Результат каждой доставки пишется в `notifications`, его видно в журнале уведомлений.

Кто что получает:

| Событие | Кому |
|---|---|
| Заявка принята | заявитель, контакт площадки |
| Назначен инженер | заявитель, инженер |
| Инженер принял задачу | заявитель, координаторы |
| Работы завершены (после приёмки акта координатором) | заявитель, контакт площадки |
| Возврат на доработку | инженер |
| Просрочка | руководители |

Telegram получают только сотрудники с номером чата в карточке. Сотрудник пишет боту `/start`, бот отвечает номером, администратор вписывает его в карточку. Отключить уведомления по событию и каналу можно в `notification_preferences`.

## Переменные

| Переменная | Значение |
|---|---|
| `DATABASE_URL` | подключение к Postgres под ролью `medtech_worker` (нужен LOGIN и пароль, см. ниже) |
| `PUBLIC_APP_URL` | адрес CRM, для ссылки на задачу в письме |
| `NOTIFICATIONS_DRY_RUN` | `true`: ничего не отправлять, только писать в журнал службы. Доставки при этом считаются отправленными, поэтому режим разрешён только с локальными `PUBLIC_APP_URL` и `DATABASE_URL` |
| `SMTP_EHLO_NAME` | имя своего узла для SMTP, по умолчанию домен адреса отправителя |
| `EMAIL_NOTIFICATIONS_ENABLED` | по умолчанию `true` |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_STARTTLS`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM_ADDRESS`, `SMTP_FROM_NAME` | почта отправителя |
| `TELEGRAM_NOTIFICATIONS_ENABLED` | по умолчанию `false` |
| `TELEGRAM_BOT_TOKEN` | токен бота от @BotFather |
| `TELEGRAM_CHAT_ID_REPLIES` | бот отвечает номером чата на `/start`, по умолчанию `true` |
| `OUTBOX_POLL_INTERVAL_MS` | частота прохода, по умолчанию 5000 |
| `MAINTENANCE_ACTIVATION_RULE`, `MAINTENANCE_ACTIVATION_LEAD_DAYS`, `MAINTENANCE_ACTIVATION_TIME_ZONE` | когда запускать ТО: в день начала периода (по умолчанию) или за N дней, по московскому времени |

## Роль базы

Роль `medtech_worker` создаётся миграциями без входа. Ей выданы только функции очереди. Для запуска выдайте вход один раз (пароль храните в настройках Dokploy, не в репозитории):

```sql
ALTER ROLE medtech_worker LOGIN PASSWORD '...';
```

## Запуск

```bash
npm ci && npm run build && npm start
```

В Docker: `docker build -t medtech-worker worker/`, контейнер в той же сети, что и база Supabase, `stop_grace_period: 30s` (служба дожидается текущей отправки до 25 секунд). Если отправка не закончилась за это время, она получит `notification_delivery_lease_expired` и не повторится, как при падении.

Ограничения настроек: `SMTP_TIMEOUT_MS` от 1 до 30 секунд (вся сессия до 4 таймаутов укладывается в аренду попытки 2 минуты), `TELEGRAM_TIMEOUT_MS` от 11 до 100 секунд (меньше аренды попытки). Если лимит попыток снизить, доставки, уже превысившие его, получат `max_attempts_exceeded` без исходной причины. Проверка здоровья: файл `/tmp/medtech-worker-ready` обновляется после каждого прохода.

Повторы: временные сбои повторяются с растущей паузой (2, 4, 8 минут и так далее, не больше 6 часов между попытками), до 12 попыток, это около суток. После последней попытки доставка сразу получает `max_attempts_exceeded`. Событие ждёт самую позднюю повторную доставку, поэтому повтор для других получателей того же события может прийти вместе с ней. Неверный адрес почты не пропускается молча: доставка видна в журнале с ошибкой `smtp_invalid_address`. Постоянные отказы (адрес отклонён, неверный адрес, бот заблокирован) не повторяются. Обрыв после передачи письма или сообщения считается неизвестным исходом и тоже не повторяется, чтобы не было дублей. Если служба упала посреди отправки, такая доставка помечается `notification_delivery_lease_expired` и не повторяется (решение студии: письмо не больше одного раза); такие записи видно в журнале.

При добавлении SECURITY DEFINER функций для службы: `REVOKE EXECUTE ... FROM anon, authenticated` и `GRANT EXECUTE ... TO medtech_worker`. Тест `supabase/tests/role_access.sql` проверяет, что лишних доступов нет.

Тесты: `npm test` (без базы и без сети).
